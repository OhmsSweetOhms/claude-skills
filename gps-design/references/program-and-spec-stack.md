## The receiver

**RF front-end (active substrate):** ZCU102 + AD9986-FMCA on the
`2048-quad-band-txm8l4` profile (ADR-007): 1.96608 GHz ADC clock, exact
GPS L1 NCO, RX 20.48 MSPS native over JESD204B. The hardware target
matrix also carries an AD9361-based divergent small-fabric target; see
the substrate bullets below and `docs/decision-log.md`.

**FPGA (PL):** Resamples the substrate rate to 4.096 MSPS via the
parametric (×N, /M) PL.INTERPOLATOR / PL.DECIMATOR ladder (ADR-007;
4096 samples/ms = 2^12 = natural FFT size). Dynamic bit-select reduces
12-bit samples to 4-bit for a time-shared correlator engine (12
channels, E/P/L I/Q) and a 4096-point FFT-based PCPS acquisition engine
(authored R2²SDF FFT, ADR-PL-B2-003). Every PL block is gated bit-exact
(`max_abs_lsb=0`) against its Python fixed-point golden.

(Not moved with these two paragraphs: the project file's third, on the PS partition. It
restates ADR-011 as amended by ADR-012 — the ADRs are its home — and `SKILL.md` §Key
Architecture Decisions warns that an all-bare-metal partition is not a current
benchmark. "The substrate bullets below" in the first paragraph are ADR-001 and
ADR-007 in `docs/decision-log.md` and `references/fpga-pl-bringup.md`.)

**Stale in the moved text, kept verbatim so the move loses nothing:** "reduces 12-bit
samples to 4-bit". PL.B1's width is ADR-PL-B1-004 (accepted): an 8-bit default, B
configurable in {2, 4, 6, 8} on the ZCU102; the 4-bit default it supersedes was
ADR-PL-B1-002 (`docs/architecture/zynq-pl/pl-b1-bit-select/decisions.md`). What the
correlator consumes is a separate question from what PL.B1 emits — read the block's
decisions before quoting a width.

## The development strategy — seven structural layers

The pipeline has seven structural layers. **Phase status, test counts,
and current measurements live in `.threads/` — query
`python3 $HOME/.claude/skills/threads/scripts/index_threads_research.py --print`
or `python run_tests.py --list` for the live picture. The bullets
below describe what each layer is, not how done it is.**

1. **Signal generation** — Python IQ generation produces scenario-rate
   test data, including the 4.096 MSPS C/A rail and 20.48 MSPS
   native L1C input used by dual-rate runs. GPS scenario engine
   (`scenario_engine/`) computes time-varying Doppler, code phase,
   C/N0, and visibility from orbital mechanics + receiver trajectory
   (static, rover, cislunar). Scenario engine Doppler profiles feed
   `gps_iq_gen` via `doppler_profiles` for time-varying synthesis.
   See `gps_iq_gen/CLAUDE.md`, `scenario_engine/CLAUDE.md`, and
   `docs/gps-scenario-engine/`.

2. **Python GPS receiver** — block-level golden model. Each Python
   block mirrors an FPGA/PS block. Nav decode (PS.B11), pseudorange
   (PS.B13), and PVT (PS.B12) are wired; LNAV subframes are
   generated by `gps_receiver/nav_gen/` (NavDataGenerator +
   SubframeEncoder + EphemerisBuilder) from the scenario engine's
   24-SV constellation. See `gps_receiver/CLAUDE.md`.

3. **Parameter optimization** — autograd-based tuning of per-block
   parameters (loop bandwidths, thresholds, spacings) using
   PyTorch/micrograd against differentiable cost functions. See
   `docs/gps-autograd-tuning/`.

4. **Visualization** — SDR viewer with VisPy 2D rendering for
   IQ/spectrum/waterfall. The 6-region shared memory architecture
   is being replaced by a unified `sdr_rx` region with per-SV
   colocated data; see `docs/spec-unified-receiver-memory.md`.

5. **Fixed-point bridge** — quantization analysis proving 4-bit
   correlator input costs <0.05 dB (Hegarty 2011). Fixed-point
   parameters are in the JSON spec stack. The receiver-level
   simulation path stays floating-point; explicit block-local
   fixed-point backends (PL.B3 `TrackingChannel(accel_backend=
   "fixed_point")`, PL.B2 `PCPSAcquisition(backend="fixed_point")`)
   are the `max_abs_lsb=0` RTL vector authorities, instantiated
   directly by tests and vector generators — never through
   `GPSReceiver`.

6. **FPGA build via SOCKS** — six phases: RF interface
   (substrate-dependent: AD9986 JESD204B active, AD9361 LVDS
   divergent), rate conversion, single-channel correlator, time-shared
   multi-channel, PCPS acquisition, optimization. Each FPGA block
   verified against its Python model via Ethernet streaming or DMA
   injection on the ZCU102 GPS-streaming HIL substrate. See
   `docs/implementation-plan-fpga-gps-receiver.md`.

7. **Extensions** — dual-frequency (second AD9361 for L2). Cislunar
   weak-signal: see `docs/implementation-plan-weak-signal-tracking.md`
   and `.research/tracking-sensitivity-analysis.md`.

## The JSON spec stack — what `SKILL.md` §The JSON Spec Stack does not carry

`SKILL.md` carries the overview, a file table and §Invariants. The project file's
versions below are the newer where the two differ: this tree names `iq_gen.epoch_utc`,
the run's one clock, and this file table says to query the profile inventory instead
of copying profile names.

```
tracking-mode-profiles.json       ← thin-pointer registry
  └── scenario_root: "<name>.v2.json"
        └── platforms.<p>.trajectory + .antennas
            entities.<e>.{platform, antenna, receiver_profile, kind}
            environment.{elevation_mask_deg, t_sys_k, cn0_floor_dbhz}
            iq_gen.{epoch_utc, doppler_type, nav_data, duration_s,
                    cn0_dbhz_default, noise_model.rms_dbfs, ...}
              └── receiver_profile (string)  → receiver-block-profiles.json
                    └── per-block params     → shared-interfaces.json
                          └── telemetry signals → monitor-signals.json
```

### File roles

| File | Purpose | Consumed By |
|------|---------|-------------|
| `scenario_engine/scenarios/*.v2.json` | **Scenario root**: receiver/platform/entity/environment/iq_gen/outputs. Validated against `scenario_engine/schemas/scenario.schema.json`. Carries exactly ONE clock, `iq_gen.epoch_utc` (required) — the UTC instant `t = 0` denotes for every transmitter and the receiver; the loader derives the run's absolute GPS seconds and `wn`/`tow` from it and nothing else may write a clock. | `gps_scenario.load_scenario_root_v2`, `_build_engine_from_scenario_json`, RINEX export |
| `scenario_engine/schemas/scenario.schema.json` | JSON Schema (Draft-07) for the v2 shape, including conditional rules per `signal_source` enum (`synthetic` / `test_24sv` / `rinex` / `live`) and per-entity-`kind` rules. | jsonschema validation in `load_scenario_root_v2` (pre + post-`--set`) |
| `tracking-mode-profiles.json` | Thin-pointer registry: every mode is `{"scenario_root": "...", "diagnostic_overlay": {...optional...}, "notes": "..."}`. Diagnostic overlays (`zero_doppler`, `doppler_ladder`, `dynamic_zero_*`) attach here so a single scenario file is reusable. | `gps_scenario.build_config(mode_name)` |
| `receiver-block-profiles.json` | Runtime parameters per named receiver profile and block. Query `profiles` for the live inventory instead of copying the keys into documentation. | `GPSReceiver(profile=...)` at init; `load_scenario_root_v2` validation chain |
| `shared-interfaces.json` | Block IDs, Python module/class, input/output interfaces, transport contracts. | Code structure, tests, FPGA build |
| `monitor-signals.json` | Telemetry signals per block with types, rates, and `source_block` attribution. | Telemetry frame packing, viewer, tests |

**Classification taxonomy:** how the scenario shape classifies things —
platform → role/mobility, entity → function (`kind`), constellation →
nav-vs-interference category + system — is defined canonically in
`docs/scenario-taxonomy.md` (settled 2026-06-11).
Read it before adding a classification field or value.

### CLI surface

`gps_scenario.py` exposes both intake shapes:

- `--mode <name>` — resolves to a thin pointer in `tracking-mode-profiles.json`, then through `load_scenario_root_v2`.
- `--scenario-root <path>` — load a v2 scenario file directly (skips the mode registry).
- `--set <key.path=value>` (repeatable) — override a v2 field. Type coercion: literal `null` → int → float → bool (`true/True/false/False`) → string. Applied post-load + post-validation; the merged dict is re-validated against the schema.

### Scenario orchestration ownership

`gps_scenario.py` is the public CLI/API and composition root. It owns
configuration loading and validation, engine and emitter construction,
scenario profiles and overlays, IQ generation and receiver execution,
replay routing, and shared orchestration services.

| Module | Ownership |
|--------|-----------|
| `gps_scenario.py` | Composition root, CLI/programmatic API, configuration and schema handling, orchestration spine, replay modes, and compatibility exports. |
| `gps_scenario_results.py` | Single- and multi-platform results-payload serialization. |
| `gps_scenario_imu.py` | IMU export formatting and sidecar-emission implementation; the root injects sensor construction and the generic sidecar writer. |
| `gps_scenario_interference.py` | Interference manifests and terrestrial/spaceborne geometry; root wrappers inject scenario, trajectory, seed, and constellation services. |
| `gps_scenario_ubx.py` | The UBX export of the epoch record and the one parser back to it (decision 157: the JSON writer and the UBX encoder are two writers of the ONE record; nothing here reads receiver state). Contract: `docs/spec-ubx-output-contract.md`. |

`gps_scenario` preserves historically imported results, IMU, and
interference helper surfaces through explicit aliases or
signature-preserving wrappers. The leaf modules do not import the
composition root at module import time, avoiding a second root module
instance during CLI execution.

### Editing rules

(The project file's other three rules — profile parameter names match the `.get()`
keys, block IDs are canonical, a `gps_receiver` entity carries `receiver_profile` —
are `SKILL.md` §Invariants.)

- **One clock per scenario.** `iq_gen.epoch_utc` is required and is the
  run's only time base. Never write `start_gps_time_s`, `wn`, or a `tle`
  platform's `trajectory.epoch_utc` — the loader derives all three and the
  schema plus `_reject_retired_clock_fields` refuse a file that writes them
  (operator ruling 2026-08-28 `one-run-epoch`).
- `shared-interfaces.json` block entries must have `module`, `class`,
  `profile_key`, `inputs`, `outputs`.
- `monitor-signals.json` uses `source_block` to attribute each signal
  to its producing block.
- `tracking-mode-profiles.json` entries contain `scenario_root`, optional
  `notes`, and an optional `diagnostic_overlay`. Scenario configuration stays
  in the scenario root. A normal new scenario may receive a mode after schema
  validation; a diagnostic mode may reuse an existing scenario root with an
  overlay.
- Each spec file's `schema_version` is its **own doc revision**, not a
  single stack-wide version — they legitimately differ (config files at
  `2.0.0` from the v2-scenario pivot; `rf.json`/`receiver.json` at `1.0.0`,
  structurally unchanged; `scenario.schema.json` carries `$schema`/`title`,
  not `schema_version`). Don't force them equal. Metadata keys are bare
  (`schema_version`/`status`/`date`/`description`) across all files — no
  underscore-prefixed (`_schema`) dialect.

### Loaders & walkers

No generic JSON walker exists — each consumer targets its files by
path or glob. Where the stack is read:

| Script | Reads | Role |
|--------|-------|------|
| `gps_scenario.py` | mode registry → `.v2` root → `receiver-block-profiles`; validates vs schema | `load_scenario_root_v2`, `build_config`, `_validate_v2_scenario` (CLI + API) |
| `gps_receiver/receiver.py` | `receiver-block-profiles.json` | `load_profile()` at `GPSReceiver` init |
| `scenario_engine/constants.py` | `rf.json` | import-time physics constants |
| `tests/test_scenario_root_schema.py` | `scenarios/*.v2.json` (glob) | schema validation; auto-discovers every shipped scenario |
| `docs/data-flow/map_data_flow.py`, `docs/control-flow/map_control_flow.py`, `docs/scenario-flow/map_scenario_flow.py` | `shared-interfaces.json` (+ mode / profiles) | DOT/SVG diagram generators |
| `$HOME/.claude/skills/threads/scripts/index_threads_research.py` | `.threads/**/thread.json`, `.threads/threads.json` | thread-registry walker (external skill) |
